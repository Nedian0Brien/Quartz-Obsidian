
## 개요
**Redis**(REmote DIctionary Server)는 오픈소스 **인메모리 데이터 구조 저장소**로, 데이터베이스, 캐시, 메시지 브로커로 사용됩니다. 매우 빠른 성능을 제공하며, 다양한 데이터 구조를 지원합니다.

**주요 특징:**
- 인메모리 저장소로 매우 빠른 읽기/쓰기 성능
- 다양한 데이터 구조 지원 (문자열, 해시, 리스트, 셋, 정렬된 셋 등)
- 영속성(Persistence) 옵션 제공
- 레플리케이션과 클러스터링 지원
- Pub/Sub 메시징 패턴 지원
- 트랜잭션 지원

## Redis가 필요한 이유
---

#### 빠른 성능
- 모든 데이터를 메모리에 저장하여 마이크로초 단위의 지연시간 제공
- 디스크 I/O를 거치지 않아 RDB보다 훨씬 빠름

#### 캐싱
- 자주 조회되는 데이터를 캐싱하여 데이터베이스 부하 감소
- TTL(Time To Live) 설정으로 자동 만료 관리

#### 세션 관리
- 분산 환경에서 사용자 세션 정보를 중앙에서 관리
- 로드밸런서 뒤의 여러 서버가 동일한 세션 정보 공유 가능

#### 실시간 순위표
- Sorted Set 자료구조를 이용한 효율적인 랭킹 시스템 구현
- 게임 리더보드, 실시간 통계 등에 활용

#### 메시지 큐
- Pub/Sub 기능으로 메시지 브로커 역할 수행
- [[Apache Airflow]], [[Kafka]] 등과 함께 사용되어 비동기 작업 처리

## 주요 데이터 구조
---

### String
가장 기본적인 데이터 타입으로, 텍스트나 바이너리 데이터 저장

```redis
SET key "value"
GET key
INCR counter    # 숫자 증가
DECR counter    # 숫자 감소
```

**사용 사례:**
- 캐싱
- 카운터 (조회수, 좋아요 수)
- 간단한 키-값 저장

### Hash
필드-값 쌍의 컬렉션 (객체 저장에 적합)

```redis
HSET user:1000 name "Dennis" age "25"
HGET user:1000 name
HGETALL user:1000
```

**사용 사례:**
- 사용자 프로필
- 설정 정보
- 객체 데이터 저장

### List
순서가 있는 문자열 리스트 (양방향 큐로 동작)

```redis
LPUSH mylist "first"
RPUSH mylist "last"
LPOP mylist
RPOP mylist
LRANGE mylist 0 -1
```

**사용 사례:**
- 최근 활동 로그
- 타임라인
- 메시지 큐

### Set
순서가 없는 고유한 문자열 집합

```redis
SADD myset "member1"
SADD myset "member2"
SMEMBERS myset
SISMEMBER myset "member1"
```

**사용 사례:**
- 태그 시스템
- 중복 제거
- 집합 연산 (교집합, 합집합, 차집합)

### Sorted Set (ZSet)
점수와 함께 정렬된 고유한 문자열 집합

```redis
ZADD leaderboard 100 "player1"
ZADD leaderboard 200 "player2"
ZRANGE leaderboard 0 -1 WITHSCORES
ZREVRANGE leaderboard 0 9  # 상위 10명
```

**사용 사례:**
- 리더보드, 랭킹 시스템
- 우선순위 큐
- 시간 기반 정렬

## Redis의 영속성(Persistence)
---

Redis는 인메모리 저장소지만, 데이터를 디스크에 저장하는 두 가지 방식을 제공합니다.

### RDB (Redis Database)
특정 시점의 스냅샷을 디스크에 저장

**장점:**
- 백업이 간단함 (단일 파일)
- 재시작 시 빠른 복구
- 성능 영향이 적음

**단점:**
- 장애 시 마지막 스냅샷 이후의 데이터 손실 가능
- 대용량 데이터셋에서 스냅샷 생성 시 성능 저하

### AOF (Append Only File)
모든 쓰기 작업을 로그 파일에 기록

**장점:**
- 데이터 손실 최소화 (1초마다 또는 매 쓰기마다 동기화 가능)
- 로그 파일이므로 복구가 안전함

**단점:**
- 파일 크기가 RDB보다 큼
- 복구 속도가 RDB보다 느림

## 캐싱 전략
---

### Cache-Aside (Lazy Loading)
애플리케이션이 캐시를 직접 관리하는 패턴

```
1. 애플리케이션이 캐시에서 데이터 조회
2. 캐시에 없으면 데이터베이스에서 조회
3. 조회한 데이터를 캐시에 저장
4. 데이터 반환
```

**장점:** 필요한 데이터만 캐싱
**단점:** 첫 요청이 느림 (Cache Miss)

### Write-Through
데이터 쓰기 시 캐시와 데이터베이스에 동시 저장

```
1. 애플리케이션이 캐시에 데이터 쓰기
2. 캐시가 데이터베이스에도 쓰기
3. 완료 응답
```

**장점:** 데이터 일관성 보장
**단점:** 쓰기 성능 저하, 사용하지 않는 데이터도 캐싱

### Write-Behind (Write-Back)
캐시에만 먼저 쓰고, 비동기로 데이터베이스에 저장

**장점:** 쓰기 성능 향상
**단점:** 캐시 장애 시 데이터 손실 위험

## Redis와 [[Apache Airflow]]
---

Redis는 Airflow의 **CeleryExecutor**와 함께 사용됩니다:
- **메시지 브로커** 역할: Celery Worker들에게 작업 분배
- **결과 백엔드** 역할: 작업 실행 결과 저장

## Redis 클러스터링과 고가용성
---

### Redis Sentinel
자동 장애 조치(Failover)와 모니터링을 제공하는 고가용성 솔루션

**주요 기능:**
- 마스터 노드 장애 감지
- 자동으로 슬레이브를 마스터로 승격
- 클라이언트에게 새로운 마스터 주소 알림

### Redis Cluster
데이터를 여러 노드에 분산 저장하는 샤딩 솔루션

**특징:**
- 16384개의 해시 슬롯으로 데이터 분산
- 자동 샤딩
- 고가용성과 확장성 동시 제공

## 주요 명령어
---

### 키 관리
```redis
KEYS pattern       # 패턴에 맞는 키 찾기 (주의: 프로덕션에서 사용 금지)
SCAN cursor        # 키를 점진적으로 반복 (프로덕션 권장)
EXISTS key         # 키 존재 확인
DEL key           # 키 삭제
EXPIRE key seconds # TTL 설정
TTL key           # 남은 시간 확인
```

### 데이터베이스 관리
```redis
SELECT index      # 데이터베이스 선택 (0~15)
FLUSHDB          # 현재 DB의 모든 키 삭제
FLUSHALL         # 모든 DB의 모든 키 삭제
INFO             # 서버 정보 확인
```

## Redis의 장단점
---

### 장점
- 매우 빠른 성능 (마이크로초 단위 응답)
- 다양한 데이터 구조 지원
- 간단한 API와 사용법
- 영속성과 복제 기능 제공
- 활발한 커뮤니티와 생태계

### 단점
- 메모리 용량 제한 (비용이 높을 수 있음)
- 단일 스레드 구조 (긴 작업이 전체 성능에 영향)
- 복잡한 쿼리나 조인 불가능
- 메모리 파편화 문제 가능성

## 언제 Redis를 사용할까?
---

**Redis가 적합한 경우:**
- 빠른 읽기/쓰기가 필요한 경우
- 캐싱이 필요한 경우
- 실시간 분석이나 순위표가 필요한 경우
- 세션 관리가 필요한 경우
- 간단한 Pub/Sub 메시징이 필요한 경우

**Redis가 부적합한 경우:**
- 복잡한 쿼리나 조인이 필요한 경우
- 대용량 데이터 저장이 필요한 경우 (비용 문제)
- 강력한 데이터 일관성이 필수인 경우
- 트랜잭션이 복잡한 경우
